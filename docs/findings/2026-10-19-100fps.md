# 100 fps end to end: sensor mode 3, the precrop stall, the shutter stretch, and a trim band narrower than a line

**Status:** shipped — mode 3 above 90 fps, the loader's aspect check, the
high-fps shutter cap and the line-scaled trim band; reference:
`docs/airtime-model.md` §3 ("Sensor mode and the shutter cap follow
`venc.fps`" and the trim bullet). The phase lock on top is
`docs/phase-lock.md`.

Bench, 2026-10-19, on `master` 5d642c0d plus the changes below. The question
was whether the encoder can run at an arbitrary rate, toward 100 fps on a
100 Hz goggle panel. The GS drove a desktop monitor whose EDID offers
2560x1440 at 99.95/75/60 Hz and nothing at 100 Hz below that (1080p and 720p
top out at 60), so `screen_mode = "2560x1440@99.95"`; DrmPresenter picked
`2560x1440 @99.946 Hz`.

## The sensor modes

`/proc/mi_modules/mi_sensor/mi_sensor0` on the IMX415 (stock OpenIPC
driver): 0 = 3840x2160@30, 1 = 2952x1656 → 2560x1440@60, 2 = 1920x1080@90
(binned), 3 = 1472x816@120. The pipeline pinned mode 2, so `venc.fps = 100`
was clamped to 90. The pipeline now takes mode 3 when `venc.fps > 90`.

## Mode 3 with a 16:9 `venc.size`: 0 fps

`venc.size = "1280x720"`, `fps = 100`: the encoder produced nothing
(`Fps_1s 0`, `IsrTotalCnt 0`; maburd looped "waiting for encoder data").
Stage counters:

| stage | reading |
|---|---|
| sensor | `fps 99` |
| VIF | `Cap_size (10,0,1450,816)`, 49.5 fps — half the sensor rate |
| VPE chn | `EnqCnt 6496`, `DropCnt 6494` — every frame dropped; MainScl `VsyncCnt` 2× `FrameDoneCnt` |
| VENC ch0 | bound `120/1 → 120/1`, input `FinishCnt 0` |

At `fps = 120` the same: sensor 119, VIF 60, VPE drops all. Mode 2 at
1080p60 on the same build was clean (VIF 61 fps, VPE `DropCnt 11`, encoder
60), with identical `hdrmode 1 / planecnt 2`, so the HDR fields are not the
difference. The keep-aspect precrop is: 1472x816 is not 16:9, so the
pipeline crops the VIF capture to 1450x816 at x = 10. With
`venc.size = "1472x816"` (no precrop) VIF ran 100 fps, VPE `DropCnt 11`, the
encoder 98.9 / 101.0 fps (1 s / 10 s). Why the crop stalls the VPE was not
investigated (alignment of the 1450 width or the x offset are the
candidates); the precrop code is waybeam's unchanged. The loader now
refuses a `venc.size` off 1472:816 above 90 fps.

## Stuck at 98.941 Hz: the AE stretch

With video flowing, the trim measured 98.941 Hz in every round while its
request climbed from 100000 to the 105000 mfps ceiling, then gave up. The
exposure cap was the whole frame period (`maxShutter 10000us`); in the dim
bench scene the AE sat at it, and the sensor's frame is the shutter plus
overhead: 10107 µs, VMAX 2056 against the 2035 a 100 fps request asks for.
At 60 fps the same stretch (3386 lines) stays under the trimmed 3391, which
is why it never showed.

Halving the cap (the waybeam "180° rule", which also pins the shutter's
minimum) moved the sensor to 100.0 Hz; that pin would overexpose in
daylight, so it was only the diagnosis. Shipped instead: above 90 fps the
cap is 90 % of the period (9000 µs at 100 fps), no minimum.

## The trim could not land: band narrower than a line

With the stretch gone the trim still gave up: its measurement flipped
99.960 / 100.010 Hz (median steps 10004 / 9999 µs). Those are adjacent
VMAX lines (2035 / 2034, ~4.9 µs a line at ~202.5k lines/s), not
measurement noise: one line is 49 mHz at 100 fps, and the band
`[fps − 0.030, fps − 0.004]` (26 mHz, sized for 60 fps's 18 mHz lines)
lies between them. Falling back to the plain 100000 mfps request left the
sensor ~0.25 Hz under its request, beyond the phase lock's ±200 mfps reach
of the 99.946 Hz panel: the lock acquired, ran out of range with the error
still drifting, and went `oor`.

The band and the one-line nudge now scale by (fps/60)² above 60 fps. The
host simulator with mode 3's VMAX (1696 at 120 fps) reproduces the bench
pair exactly (VMAX 2035 = 99.959 Hz, 2034 = 100.008 Hz); with the old band
it never locks.

## Result

Shipped build, `venc.size = "1472x816"`, `fps = 100`, dim bench:

- `Exposure cap: maxShutter 10000us -> 9000us (for 100 fps)`
- `[sensor] cal: round 1 measured 99.721 Hz -> request 100269 mfps`,
  `locked, request 100269 mfps measured 99.960 Hz after 1 round(s)`
- GS phase lock: 10 windows `acq`, then `lock` and held (61/61 windows in
  the next minute), offset −90 mfps.
- Over 60 s locked: 100 frames presented per second, `late` +0, `pdrop`
  +0, `skips` +0, `replaced` +1.
- `lat:` e2e 27–28 ms p50/p90 (enc 5, air 1–3, fec 3–8, dec 3–4, reg
  10–12, dsp 4).

## Open

- The field of view of mode 3 against mode 2 was not compared (1472x816
  is likely a crop of the array, so a narrower view).
- Why a keep-aspect precrop of mode 3 stalls the VPE; a 16:9 output (for a
  1280x720 or 1920x1080 panel) needs it or a stretch.
- A 100 Hz goggle panel was not tested: the monitor's 100 Hz mode is
  2560x1440 only. A goggle input's EDID decides whether 100 fps is
  showable there.
- Not flown; the link ran at the bench's rung, not across a ladder.
